# 中立油井重建：阵亡者的油井变回中立无敌井

> ★ 2026-10 作者定案：中立油井是**默认规则的一部分**，属于理所当然的机制，
> **不做任何公屏播报**（ChoukaT.oilCenterRebuilt / oilSeatRebuilt / oilSeatCaptured 三个文案已删除）。
> 只在日志里留痕，关键词见 §8。玩家侧唯一的可见反馈就是油井本身变了颜色 + 每秒 +40 的进账。

> 对应代码：`scripts/lua/chouka/30_world/08_oilfield.lua`（节点「油井重建」，21 号节点）
> 相关代码：`30_world/06_center.lua`（中央油井占点）、`20_economy/01_income.lua`（收入）

---

## 0 一句话

**油井被"清场"带走之后，原地重生一口「中立 + 无敵」的同名油井，谁占住谁收钱。**

- 中央 `centerOil1/2` —— 被玩家占领后，该玩家一旦阵亡，井跟着消失 → 重建，可重新抢。
- 玩家 `oil1~oil6` —— 岛主阵亡时系统会清掉他名下所有东西（含这口不可摧毁的油井）→ 重建为中立井，变成**战胜者的战利品**。
- **空位永不重建**：不满 6 人的局，那个位置本来就没有起重机和油井。

---

## 1 两个问题现象

### 1.1 中央油井会"被玩家带走"

原图中央两座油井 `centerOil1` / `centerOil2` 在地编里是 **中性（`/team`）+ 不可摧毁**。
`06_center.lua` 的占点逻辑抢到之后会调

```lua
ExecuteAction("NAMED_TRANSFER_OWNERSHIP_PLAYER", oil, "Player_" .. leadIndex)
```

—— 归属真的转给了玩家（油井颜色跟着变，视觉反馈是对的）。
但**一旦这个玩家阵亡/退出，引擎清场会把这口井当成"他的建筑"一起杀掉**，中央油井从此永久消失，
`ChoukaCenterOilObj[k]` 变成死句柄，`ChoukaFindCenterOils()` 按真名找也找不回来（几何兜底也找不到），
整块中央油井玩法就废了。

### 1.2 玩家油井会被"清场"抹掉

`oil1~oil6` 在地编里同样是 **不可摧毁**（`docs/02` §3）。也就是说：

- 敌人打不掉它；
- 它**唯一**的消失方式是"岛主被清场，系统连人带东西全杀"。

所以玩家出局之后，他的岛上就永久少了一口油井 —— 而这块地本来是打赢的人应得的奖励。

---

## 2 为什么"无敌"不会阻止清场（关键前提）

这一条是整个方案能不能成立的地基，作者实测已经给出答案：

> 中央油井在地编里标了「不可摧毁」，被玩家占领后该玩家阵亡 —— **油井照样爆了**。

说明引擎的玩家阵亡清场是**强制移除**，不是走伤害流程。所以：

| 手段 | 挡得住敌人打吗 | 挡得住阵亡清场吗 |
|---|---|---|
| 地编「不可摧毁」 | ✅ | ❌（实测） |
| `AttributeModifier_INVULNERABLE` | ✅ | ❌（同上，同属"不可损坏"语义） |

结论：给重建出来的井挂无敌，既能防止被人恶意打掉，又不会妨碍"占领者阵亡 → 井重新变回中立"的循环。

> ⚠ 万一实测发现 `AttributeModifier_INVULNERABLE` **确实**挡住了清场（和地编标志行为不同），
> 井会残留成一个"死人的井"。代码里已经埋了兜底：扫描时如果发现占领者的起重机已经没了，
> 就把归属释放回中立（`ChoukaOilOwner[seat] = 0` / `ChoukaCenterOilOwner[k] = 0`），
> 收入立刻停止，其他人可以照常重新占领。见 §4.6。

## 3 实现

### 3.1 新增节点

`tools/sync-scriptsdata.js` 里在「中央油井」后面插了一条：

```js
{
    file: 'lua/chouka/30_world/08_oilfield.lua',
    folder: '抽卡hex',
    name: '油井重建',
    evaluationInterval: 1,
    deactivateUponSuccess: false,
}
```

一秒节点。节奏靠内部计数器切分：

| 频率 | 干什么 |
|---|---|
| 每秒 | `ChoukaOilPaySpoils()` —— 给"占领了阵亡者油井"的玩家发钱 |
| 每 5 秒 | `ChoukaOilRebuildCenter()` + `ChoukaOilScanSeats()` —— 重建扫描 + 占点推进 |

### 3.2 状态表

全部是全局表（Lua 桥的函数拿不到外层 `local`），键都是**座位号 1~6**：

| 表 | 含义 |
|---|---|
| `ChoukaOilArmed[seat]` | `1` = 这个座位本局真的参战（**起重机和油井都在**）。`nil` = 空位，**永不重建** |
| `ChoukaOilPos[seat]` | 原坐标 `{x,y,z}`，重建就落在这个点 |
| `ChoukaOilObj[seat]` | 当前那口井的句柄（原装的或我们重建的） |
| `ChoukaOilRebuilt[seat]` | `1` = 这口井已经是**中立据点**（`重建出来的` 或 `原装井被释放的`）。**只有这种井才走占点** |
| `ChoukaOilCraneSeen[seat]` | `1` = 至少见过一次这台起重机活着。**判"阵亡"的前提**，见 §4.6 |
| `ChoukaOilOwner[seat]` | 占领者 `0` = 中立 |
| `ChoukaOilScore/Chall[seat]` | 占点进度 / 正在挑战的玩家 |
| `ChoukaOilGone[seat]` | 连续几次扫描找不到它（防"清场还没走完就重建"） |
| `ChoukaCenterWellPos[k]` | 中央油井 `k` 的原坐标 |
| `ChoukaCenterWellGone[k]` | 同上，连续找不到的次数 |

### 3.3 生成原语

```lua
ExecuteAction("UNIT_SPAWN_NAMED_LOCATION_ORIENTATION",
    name,                        -- 脚本名：沿用原名字（centerOil1 / oil3 …）
    typeName,                    -- 类型：按点位选，见下方"两个模型"
    team,                        -- 中立队名，见下
    { X = pos.x, Y = pos.y, Z = pos.z },   -- 坐标可以直接传 table
    0)                           -- 朝向

obj = GetObjectByScriptName(name)
ObjectLoadAttributeModifier(obj, "AttributeModifier_INVULNERABLE", 999999)
```

**两个模型（关键）**：地编里两处挂的**不是同一个单位**，重生必须照原位选：

| 点位 | 原装模型 | 重生用 |
|---|---|---|
| 玩家岛 `oil1~6` | `OilDerrick_OnWater`（**水上版**） | `CHOUKA_OIL_TYPE_SEAT` |
| 中央 `centerOil1/2` | `OilDerrick`（陆地版） | `CHOUKA_OIL_TYPE_CENTER` |

生成循环是「先试该点位该用的模型 × 三个中立队名，全失败再换另一个模型 × 三个队名」，
所以某一版引擎不认 `OilDerrick_OnWater` 也还有退路（会打一条 `_LOG` 说明用了哪个模型）。

**为什么沿用原名**：`06_center.lua`、`ChoukaFindCenterOils()` 都是按真名 `centerOilK` 找井的。
重建出来的井也叫 `centerOilK`，那么重建之后 `06_center.lua` 的占点逻辑**一行都不用改**就自动接管了；
玩家油井同理，`oilN` 这个名字在扫描里也是唯一的判据。

**中立队名按顺序试**（`CHOUKA_OIL_TEAMS`）：

| 顺序 | 队名 | 依据 |
|---|---|---|
| 1 | `/team` | 原图中央油井就是"无主玩家"（playerName 为空）→ 队名就是 `/team` |
| 2 | `PlyrCivilian/teamPlyrCivilian` | 本图玩家表 index 2 存在；赤壁/DSA 大量用作中立生成方 |
| 3 | `PlyrNeutral/teamPlyrNeutral` | 本图玩家表 index 1，`PlayerTemplate:Neutral` |

试成功的下标记在 `ChoukaOilTeamGood`，后面直接用，不再重复试错；三个都失败就打 `_LOG` 放弃。

> 注意本图玩家表里**没有 `PlyrCreeps`**（见 `docs/02` §2），所以别照抄赤壁的队名。

## 4 关键设计决定

### 4.1 空位凭什么判定"没有油井"

不是靠"油井在不在"，而是**同时要求起重机和油井都存在**：

```lua
if ChoukaOilPosOf(GetObjectByScriptName("crane" .. i)) ~= nil then
    pos = ChoukaOilPosOf(GetObjectByScriptName("oil" .. i))
end
```

- 作者实测：不满 6 人的局，空位**既没有起重机也没有油井**。
- 双条件比单条件稳：就算某版地图在空位留下了孤儿 `oilN` 对象，只要没有起重机就不会被登记。

登记只做**一次**（`ChoukaOilArmedOnce`），发生在开局门控通过后的第一次求值。
之后 `ChoukaOilArmed[seat]` 不再变，所以重建逻辑永远碰不到空位。

### 4.2 为什么中央油井的重建交回 `06_center`

| 谁 | 干什么 |
|---|---|
| `08_oilfield.lua` | 只负责**生成**，生成完把句柄写进 `ChoukaCenterOilObj[k]` |
| `06_center.lua` | 照旧负责**占点**（`ChoukaCenterLeader` + `ChoukaCenterTickCapture`） |
| `01_income.lua` | 照旧负责**收入**（读 `ChoukaCenterOilOwner[k]`） |

好处：**已验证通过的三条老路径一行都不用改**。新节点只往里面"补一口井"，不抢职责。

两个节点都是 1 秒节拍、谁先跑不保证，所以：

- `08` 里对 `ChoukaCenterOilObj/Owner/Score/Chall` 也写了一遍 `or {}`，谁先跑谁建表，不会互相覆盖；
- `06_center` 的 `ChoukaFindCenterOils()` 只在"两座都活着"时提前返回。重建写出句柄后它就是活着的，
  于是 `06_center` 直接复用；万一它先跑、把空槽位清空了，下一个节拍 `08` 又会写回去，**最多差 1 秒**。

### 4.3 玩家油井的占点：只在"重建之后"才进行

原装的那口 `oilN` 是岛主自己的私油井，收入由 `01_income.lua` 的私油井规则给（+20/s）。
如果也让它走占点，就会出现"岛主站在自己井上 → 15 秒后被判定占领自己的井 → 播报
`Player_1 占领了 Player_1 留下的油井`"这种荒谬结果。

所以占点的开关是 `ChoukaOilRebuilt[seat] == 1`：**只有我们重建出来的中立井才参与争夺。**

### 4.4 为什么战利品收入放在本节点，而不是 `01_income.lua`

`01_income.lua` 是**已实测通过**的收入主路径（底薪 / 私油井 / 中央油井 / 主公加成）。
战利品收入逻辑自成一体、数据也全在本节点手里，塞过去只会让那条已经验证的路径变复杂。
本节点同样是 1 秒节拍，收入口径一致（也吃 `CHOUKA_ECONOMY_MULT` 经济倍率）。

### 4.5 重建延迟

`ChoukaOilGone[seat]` 累加，超过 `CHOUKA_OIL_REBUILD_WAIT` 才重建。
默认 `1` → 下一次扫描（约 5 秒）就重建。

**不会重复生成**：`obj` 为空才走重建，而 `obj` 是通过"句柄 + 按真名再找一次"双路确定的。
只要旧井还在，按真名一定找得到，就走不到重建分支。

### 4.6 兜底：不依赖"系统清场一定成功"

整条链路上有两个不确定因素：**无敌会不会挡住清场**、**引擎会不会按时移除对象**。
所以判"阵亡"和"井没了"这两件事都不靠猜，而是三层处理：

**第一层：怎么确认一位玩家阵亡**

```lua
function ChoukaOilSeatKnownDead(seat)
    if ChoukaOilCraneSeen[seat] ~= 1 then return 0 end   -- 从没见过它活着 → 不下结论
    if ChoukaOilCraneAlive(seat) == 1 then return 0 end  -- 现在还活着
    return 1
end
```

`ChoukaOilCraneSeen[seat]` 在**开局登记时**置 1（那次已经确认起重机存在），
之后每次扫描只要还活着就继续置 1。

> 为什么不能直接写 `if 起重机没了 then 阵亡`：`GetObjectByScriptName` 偶发取不到时，
> 会把**活人**误判成阵亡 —— 那会立刻把全场 6 口私油井都变成可争夺据点，一局就乱了。
> 加一层"先见过活着"的门槛，误判窗口就没了。

**第二层：井还在，但岛主/占领者已确认阵亡**

不指望系统清场一定把它删掉，直接把这口井**转成中立据点**：

```lua
ChoukaOilRebuilt[seat] = 1   -- 参与占点
ChoukaOilOwner[seat]   = 0   -- 归属清空
```

`ChoukaOilRebuilt` 一旦置 1，这口井就自动进入占点循环，其他人站上去 15 秒就能抢。
代价是**队色还挂在出局玩家身上**（脚本没有干净的"转成空名玩家"原语），
但等第一个人抢到，`NAMED_TRANSFER_OWNERSHIP_PLAYER` 会把颜色一起修正。

中央油井同理：拥有者确认阵亡 → `ChoukaCenterOilOwner[k] = 0`，`01_income.lua` 立刻停止给死人发钱。

**第三层：井真的没了**

走 §3.3 的 `UNIT_SPAWN_NAMED_LOCATION_ORIENTATION` 原地重建，并把新的句柄写回各自的表。

三层叠加之后：

| 实际发生的事 | 结果 |
|---|---|
| 系统清场删掉了井 | 第三层重建 ✓ |
| 无敌挡住了清场，井留着 | 第二层转中立据点 ✓ |
| 两者都发生了（中央井删了、玩家井留着） | 各自走对应那层 ✓ |
| 什么都没发生（玩家还活着） | 井保持原样，不参与占点 ✓ |

## 5 参数表

全在 `08_oilfield.lua` 顶部，想调手感改这几行就够：

| 常量 | 默认 | 说明 |
|---|---|---|
| `CHOUKA_OIL_SCAN_EVERY` | `5` | 几秒扫一次（重建 + 占点） |
| `CHOUKA_OIL_CAPTURE_AT` | `3` | 同一人连续领先几次算占领（3 × 5 秒 ≈ 15 秒，与中央油井一致） |
| `CHOUKA_OIL_REBUILD_WAIT` | `1` | 连续几次扫描找不到才重建 |
| `CHOUKA_OIL_SPOILS_INCOME` | `40` | 占领阵亡者油井后 **$/秒**（中央油井同档） |
| `CHOUKA_OIL_INVULN_TICKS` | `999999` | 无敌时长；每次扫描都重刷，等效永久 |
| `CHOUKA_OIL_TYPE_SEAT` | `"OilDerrick_OnWater"` | **玩家岛**（水上）重生时用的模型 |
| `CHOUKA_OIL_TYPE_CENTER` | `"OilDerrick"` | **中央小岛**（陆地）重生时用的模型 |
| `CHOUKA_OIL_TYPE_ALTERNATES` | `{"OilDerrick_OnWater", "OilDerrick"}` | 兜底顺序：首选模型生成不出来就换另一个 |
| `CHOUKA_OIL_TEAMS` | 见 §3.3 | 中立队名候选，按顺序试 |

> ⚠ **两处用的不是同一个模型**（2026-10 实测修正）：地编里玩家岛 `oil1~6` 挂的是
> `OilDerrick_OnWater`（水上版），中央 `centerOil1/2` 挂的是 `OilDerrick`（陆地版）。
> 早期版本重生时统一用了 `OilDerrick`，结果玩家岛上重生出来的井和原装长得不一样。
> 现在按点位分别指定，并且带"换另一个模型再试一次"的兜底。

> `CHOUKA_OIL_RADIUS = 200` 只是**文档用**的说明值 —— 实际扫描半径用的是
> `06_center.lua` 的 `CHOUKA_CENTER_RADIUS`，因为计数函数是复用的同一个 `ChoukaCenterLeader`。

## 6 收入对照

| 来源 | $/秒 | 由谁发 |
|---|---|---|
| 底薪 | 20（三国杀主公 ×1.5 = 30） | `01_income.lua` |
| 自己岛上的私油井 `oilN` | 20 | `01_income.lua` |
| 中央油井 `centerOilK`（含重建的） | 40 | `01_income.lua` |
| **阵亡者留下的油井（重建出来的）** | **40** | **`08_oilfield.lua`** |

一口重建井被占领 = 一口中央油井的收益。6 人局全打光理论上最多 +240/s，但每座都要**独占站 15 秒**才拿得到，
实际很难全收 —— 这是"打赢的人有奖励"和"别滚雪球"之间的折中。嫌多就把 `CHOUKA_OIL_SPOILS_INCOME` 调到 20。

## 7 顺带改动：`center1~6` 箱子归属（作者 2026-10 挪点位）

作者把 `center1~6` 从中心小岛挪到了 6 条"玩家 ↔ 中心"的连接路上，避免箱子全挤中间。
代码侧检查结论：

| 位置 | 是否受影响 | 说明 |
|---|---|---|
| `06_center.lua` 刷中央箱 | ❌ 不用改 | 按航点**名字**取坐标（`CHOUKA_CENTER_CRATE_WPS` 七个点位），挪位置完全透明 |
| `07_crates.lua` 保留点位表 | ❌ 不用改 | `CHOUKA_CRATE_KEEP_WPS` 存的是名字，`ChoukaCrateNearKeepPoint` 每次现场查坐标 |
| `17_ai.lua` 中央扫描 | ❌ 不用改 | 用的是中心航点 `center` |
| `03_start.lua` 锁视角 | ❌ 不用改 | 同上 |
| **`06_center.lua` 箱子归属** | ✅ **改了** | 原来"按中央油井归属交替分两堆"的规则不再合适（见下） |

原来：

```lua
local oilOwner = ChoukaCenterOilOwner[mod(k, 2) + 1]   -- center1/3/5 → 2 号井，center2/4/6 → 1 号井
```

这个规则成立的年代，6 个点位是**围着两座中央油井的一圈**，按井分堆是合理的。
现在每个点位落在某位玩家的必经路上，再按井分堆就怪了。

改成 **`ChoukaCenterCrateOwner(wp)`：分给离这个点位最近、且起重机还活着的玩家**。

- 自适应当前布局，不需要手工维护映射表；
- 箱子本身谁都能捡，这里只管归属颜色；
- 找最近时跳过已阵亡玩家，避免箱子挂在一个死人的队色上。

## 8 待实测项

1. **`/team` 能不能生成对象** —— 三个候选队名会自动降级，日志里会写
   `油井重建：centerOil1 生成成功（模型 OilDerrick / 队名 /team）`。搜这条就知道落到了哪个模型+队名。
2. **重建井的位置/朝向** —— 坐标直接沿用原油井，朝向写 0。如果井"歪着"或者嵌进地里，
   把 `ChoukaOilSpawnNeutral` 里最后的 `0` 改成合适的角度。
3. **无敌是否挡清场** —— 见 §4.6。观察：占领者阵亡后井是消失了（理想）还是留着但归属被释放（兜底生效）。
4. **重建井能不能被再占领** —— 站上去 15 秒后油井应该归你，并且每秒 +40（**不再播报**，只有日志）。
5. **空位不刷井** —— 开 2 人局，确认 3~6 号位置**始终没有**中立油井出现。
