## 1 总览：这层东西是怎么挂上去的

整套三国杀只在两个全局变量上挂载：

```lua
CHOUKA_MODE        -- 0 = 默认玩法（拆起重机争夺）；1 = 三国杀模式
CHOUKA_GAME_STARTED -- 现有全场开局门控，**只在三国杀 Stage 3 才置 1**
```

**关键设计**：`CHOUKA_GAME_STARTED` 现在被 7 个业务节点当门控（见下表）。
三国杀把「发身份」放在 `CHOUKA_GAME_STARTED` **之前**，于是发身份、偏好投票这段时间里
这 7 个节点全部静止 —— **不用给它们加任何判断**。

| 节点 | 门控位置 | 三国杀模式下是否需要改 |
|---|---|---|
| `抽卡hex/收入` | `01_income.lua:9` | 否 |
| `抽卡hex/私有箱` | `02_private_box.lua` | 否 |
| `抽卡hex/保底军犬` | `05_dog.lua` | 否 |
| `抽卡hex/中央油井` | `06_center.lua` | 否 |
| `抽卡hex/发技能` | `14_grant_draw.lua` | 否 |
| `抽卡hex/按钮栏` | `16_buttons.lua` | 否 |
| `抽卡hex/HUD` | `20_hud.lua` | 否（仅新增一条常驻文字，见 §6②） |

新增的只有「结算后停止发钱」这一个门控 `CHOUKA_BANG_ENDED`（见 §9④）。

## 2 配置页：房主多一个「玩法」档

### ① 现状

房主配置页是 `exShowCustomBtnChoiceDialogForPlayer`，靠 `ChoukaStartShowDialog()`
（`03_start.lua:176-188`）把参数**补齐到 10 个**再 `call()`：

```
{ playerName, dialogId, title, btn1, btn2, btn3, btn4, btn5, btn6, btn7 }
   ← 3 个固定 3 ────────────────────── 最多 7 个按钮 ──────────────────────→
```

日冕文档原话（`教程.lua:389`）：**「为特定玩家显示按钮选项弹框(最多7个按钮竖着排）」**。
现在用了 4 个（2 个箱子选项 + 确认 + 重看公告）→ **还剩 3 格**。

### ② 按钮布局（改后共 6 个，仍在上限内）

| 按钮 | 文本 | 点击写入 |
|---|---|---|
| 1 | 箱子范围：全阵营 `√` | `ChoukaStartScopeKey = 1` |
| 2 | 箱子范围：只有自己 | `ChoukaStartScopeKey = 2` |
| 3 | 玩法：默认 `√` | `CHOUKA_MODE = 0` |
| 4 | 玩法：三国杀 | `CHOUKA_MODE = 1` |
| 5 | **确认，开始游戏** | `ChoukaStartConfirm = 1` |
| 6 | 重新查看公告 | 重开公告 |

### ③ ★ `CHOUKA_MODE` 必须「点击即写入」，不能等确认

现有代码本来就是「点击写 `ChoukaStartScopeKey`、确认时才读出来应用」
（`03_start.lua:352` 写入 / `:273-276` 应用）。`CHOUKA_MODE` **照抄这个节奏**：

```lua
-- 点「玩法：三国杀」的瞬间就生效
CHOUKA_MODE = 1
```

**为什么不能等确认**：`13_frame_loop.lua:9` 的保险丝判的是
`CHOUKA_GAME_STARTED ~= 1 and ChoukaFrameCount > 2700`。如果 `CHOUKA_MODE`
等确认才写，房主在公告页思考超过 3 分钟时它还是空的，保险丝就会**用默认玩法强行开局**，
「无限等待」直接失效。

点了「玩法：三国杀」后立刻写 → 保险丝马上让位（见 §3③）；
房主改回「玩法：默认」→ `CHOUKA_MODE = 0` → 保险丝立刻重新生效，和现在完全一致。

### ④ 代码落点

`ChoukaStartHostChoices()`（`03_start.lua:190-204`）和 `ChoukaChoice_start()`
（`03_start.lua:338-377`）现在都假设「只有一组选项」，要扩成两组：

```lua
ChoukaStartScopeOptions = { [1] = {scope = 0, name = ...}, [2] = {scope = 1, name = ...} }   -- 现有，不动
ChoukaStartModeOptions  = { [1] = {mode  = 0, name = "玩法：默认"}, [2] = {mode = 1, name = "玩法：三国杀"} }  -- 新增

local scopeN    = getn(ChoukaStartScopeOptions)          -- 2
local modeN     = getn(ChoukaStartModeOptions)           -- 2
local confirmBtn = scopeN + modeN + 1                    -- 5
local rereadBtn  = scopeN + modeN + 2                    -- 6
```

`btnIndex` 先落到箱子组（1..2），再落到玩法组（3..4），最后 5/6 是确认/重看。

## 3 开局状态机

### ① 四个阶段

| Stage | 名字 | 进入条件 | 结束时做什么 |
|---|---|---|---|
| 0 | 未启动 | 进游戏 | `ChoukaStartBegin()` |
| 1 | **等房主** | Stage 0 的下一帧 | 房主点「确认，开始游戏」 |
| 2 | **偏好投票**（仅三国杀） | Stage 1 结束且 `CHOUKA_MODE == 1` | 全员确认 或 180 秒超时 |
| 3 | **正式开始** | Stage 1 结束且 `CHOUKA_MODE == 0`，或 Stage 2 结束 | — |

现有的 `ChoukaStartStage`（0/1/2）**不动**，三国杀另开一整套：

```lua
ChoukaBangStage   -- 0 = 未进入；1 = 偏好投票中；2 = 已发身份；3 = 已结算
```

两个 Stage 变量互不干扰 —— 这点很重要，因为 `13_frame_loop.lua:11` 的兜底会写
`ChoukaStartStage = 2`，如果三国杀复用同一个变量会被踩坏。

### ② `ChoukaStartFinish()` 拆成前后半段

现在 `ChoukaStartFinish()`（`03_start.lua:268-...`）一口气做完所有事。要拆开：

| 半段 | 动作 | 何时执行 |
|---|---|---|
| **前半段** | `LOCK_CAMERA 0` / `LOCK_CAMERA_SCROLL 0` / `ENABLE_INPUT` | 偏好投票**之前**（否则点不到卡片） |
| | 隐藏公告 / 显示单位操作区 | 同上 |
| **后半段** | `CHOUKA_GAME_STARTED = 1` | 偏好投票**之后** |
| | `CHOUKA_DRAW_SCOPE` 应用 | 同上 |
| | `CHOUKA_BOX_LEFT = CHOUKA_BOX_SECONDS` + `SET_MILLISECOND_TIMER "box"` | 同上 |
| | `PLAYER_CAMERA_MOVE_TO` 回各自出生点 | 同上 |

> ⚠️ 顺序有讲究，沿用文件里既有的告诫（`03_start.lua:265-267`）：
> Lua 4.0 **没有 `pcall`**，标志位与"钱 / 倒计时"先做，关窗口、挪相机这类装饰动作放最后 ——
> 中间某句报错也不该把开局的关键动作挡掉。

### ③ `13_frame_loop.lua` 的保险丝让位

现在（`13_frame_loop.lua:5-31`）：

```lua
if CHOUKA_GAME_STARTED ~= 1 and ChoukaFrameCount > 2700 then
    ... 强制开局 ...
end
```

2700 帧 ≈ 3 分钟（`docs/06:128`：「进游戏 3 分钟（2700 帧）还没开局（Lua 报错 / 房主掉线 /
没人点），就强制放行」）。**这不是设计时长，是防死锁的保险丝**。

改法 —— 三国杀模式下**整条让位**：

```lua
if CHOUKA_GAME_STARTED ~= 1 and ChoukaFrameCount > 2700 then
    if CHOUKA_MODE == 1 then
        -- 三国杀模式：Stage 1 无限等房主（房主掉了就重开，同自走棋）
        --             Stage 2 由 32 号节点的 180 秒超时接手
    else
        ...现有兜底原样不动...
    end
end
```

默认玩法下这段等价于原样 → **零回归**。

```lua
ChoukaBangSeats = {}
for i = 1, 6, 1 do
    if ObjectIsAlive(GetObjectByScriptName("crane" .. i)) then
        tinsert(ChoukaBangSeats, i)
    end
end
ChoukaBangPlayerCount = getn(ChoukaBangSeats)
```

## 5 身份偏好投票

照《赤壁 2.6》的 `BangPreferenceUi`（`Bang_159_code.txt:149-168`）。

### ① 面板载体：**复用原生选择页 + 文字选项**（★ 2026-10 作者定案）

> 第一版是自绘卡片（`exCreateCustomButtonForPlayer` + 贴图 + 自定义文字，5 张 200×200 卡 + 确认键，
> 索引 1201~1206 / 1231~1241 / 1306）。作者实测后明确要求：**不要搞自定义按钮和图标，
> 直接复用房主选择页那种原生选择页和文字选项**。所以整段自绘 UI 已删除。

现在用的是**同一个原生控件**：`exShowCustomBtnChoiceDialogForPlayer`
（房主配置页 `03_start.lua:185` 和交易市场 `16_buttons.lua` 都用它）：

```lua
-- 固定 10 参：玩家名 + 面板 id + 标题 + 最多 7 个选项，不足补空串
local args = { playerName, CHOUKA_BANG_PREF_DIALOG, ChoukaT.bangPrefTitle }
-- 再 tinsert 5 个文字选项
call(exShowCustomBtnChoiceDialogForPlayer, args)
```

一屏 5 个文字选项：

```
主公（名额 1）
忠臣（名额 1）
反贼（名额 2）
内奸（名额 1）
弃权（随机分配）
```

| 项 | 值 | 说明 |
|---|---|---|
| 面板 id | `CHOUKA_BANG_PREF_DIALOG = 730` | 已占用：701~706 市场、711~716 塔、810 公告、811 房主配置 |
| 选项数 | 5 | 上限 7（10 参 − 3 固定） |
| 标题 | `ChoukaT.bangPrefTitle` | `三国杀 · 选择你想要的身份` |
| 选项文字 | `ChoukaT.bangPrefOption` | `%s（名额 %d）`，名额由 `ChoukaBangRoleCountOf` 现算 |
| 弃权项 | `ChoukaT.bangPrefAbstain` | `弃权（随机分配）` |
| 回调 | `ChoukaChoice_bangPref(playerName, btnIndex, dialogId)` | 由 `16_buttons.lua` 的 `onUserBtnChoiceDialogEvent` 分发，参数顺序照 `03_start.lua:389` |

> 收益：节点 payload 从 31.5 KB 降到 26 KB；不再占用 1201~1306 那一整段自定义索引；
> 视觉和房主配置页完全一致，玩家不需要学第二套 UI。

### ② 交互：一步到位，且**只弹给真人**

> ⚠ **两次实测修正，都是血泪：**
>
> **第一次**：靠 `EvaluateCondition(..., "Human")` 判真人 → 本图对它返回空 →
> 判出 0 个真人 → 走"没有真人就直接随机"→ **面板从来没出现过**，
> 房主确认后 1 秒就发身份开局，日志里连一条偏好文案都没有。
>
> **第二次**：改成"给全部参战座位都弹"→ 真人那份**还没选就被"别人"关掉了**。
> 根因：按钮选择对话框在引擎里只有一个"当前显示位"（详见 `docs/03` §8.3），
> 给别的座位 Show 一次会顶掉当前这份，任何座位应答/关闭收掉的也是同一份。

**现在的做法**（`ChoukaBangPrefCollectSeats`）：

| 顺序 | 取谁 | 说明 |
|---|---|---|
| ① | `ObjectPlayerScriptName("<1st Human Player>")` | 本图唯一可靠的真人接口（`docs/03` §8.2） |
| ② | `ChoukaStartHost` | `03_start` 认出来的房主（同一接口，自动去重） |
| ③ | 兜底 `Player_1` | 两个都没拿到时的最后保险 |

**只给这些座位弹面板**；其余座位（AI）的身份直接随机 —— 正好是它们本来的行为，
而且它们本来也不会点。

- **点一个选项就算定了**：`ChoukaBangPref[playerName] = 身份名`、`ChoukaBangReady[playerName] = 1`，
  随即自动关面板 + 私发一条 `你选择了：%s`
- 没有"再点确认"这一步（原生选择页点完就关，一步到位）；单真人局**选完立刻开局**
- 玩家把面板点叉了也不怕：没选的话每 `CHOUKA_BANG_PREF_REOPEN_EVERY`(=30) 秒**重弹一次**

### ③ 收尾规则：四条，先满足哪条就走哪条

| 顺序 | 条件 | 说明 |
|---|---|---|
| ① | **该弹的座位都选过了** | 单真人局 = 选完立刻发身份 |
| ② | （已并入 ①：现在只给真人弹，两者等价） | 保留给将来多真人场景 |
| ③ | **有人选过，且已静默 `CHOUKA_BANG_PREF_GRACE`(=15) 秒** | 多真人时先选完的人不用陪着等 |
| ④ | 硬超时 `CHOUKA_BANG_PREF_SECONDS`(=180) 秒 | 没选身份的按**弃权** |

> 手感说明：真人选完大约 **15 秒**进游戏（而不是 180 秒）。
> 想再快点就把 `CHOUKA_BANG_PREF_GRACE` 调小；想让人慢慢想就调大。

用**秒级节点自增计数**，不用帧数：

```lua
ChoukaBangPrefTick = ChoukaBangPrefTick + 1        -- 每个 1 秒节点 +1
if ChoukaBangPrefTick >= CHOUKA_BANG_PREF_SECONDS then ... auto ... end
```

> 为什么不用帧：`docs/07:134` 提醒过「`EvaluationInterval = 0` 若并非严格每帧，
> 按实际倍数调整」。秒节点天生准，`03_start.lua` 的 `ChoukaStartTick` 也是这么干的。

### ③b 兜底自启（防止整段被静默跳过）

`32_bang_pref.lua` 的节点体里还有一道保险：

```lua
if ChoukaStartBangPath == 1 and ChoukaBangStage == 0 and ChoukaBangPrefDone ~= 1 then
    ChoukaBangBeginPreference()      -- 幂等：已在投票中的会直接 return 1
end
```

这样即使 `03_start.lua` 的确认回调那条路没把 `ChoukaBangBeginPreference` 叫到，
偏好阶段也不会再被静默跳过。**任何一次跳过都会在日志里留下原因**
（`三国杀：偏好跳过（…）`），下次排查不用再猜。

### ④ 洗牌与名额满足（照 `Bang_160_code.txt` 的 `BangBuildShuffledPlayers`）

```
1. 统计每个身份的剩余名额 = 表中数量
2. 第一轮：按「偏好」分配 —— 若该身份名额 > 0 且此人偏好它，就给他，名额减 1
3. 第二轮：剩下的人 → 洗牌后依次填进剩下的名额
4. 主公名额恒为 1：「主公」被偏好时，先到先得
```

洗牌用 Fisher–Yates，随机源是工程既有的 **`GetRandomNumber()`**（返回 0..1，
`02a_crate_list.txt:86` 等处已用）：

```lua
-- Lua 4.0 没有 % 运算符，取模一律 mod()
local j = floor(GetRandomNumber() * i) + 1
```

> 不能用 `RandomHelper.shuffle` —— 那是赤壁的 LuaLib，本工程没有。

## 6 身份下发与信息可见性

### ① 开局私发（照 `Bang_160_code.txt:223-235` 的 `RolesShow`）

```lua
exAddTextToPublicBoardForPlayer(playerName, format(ChoukaT.bangYourRole, 身份名), 10)
```

### ② 顶部「情报」按钮的悬浮框 = 常驻情报面板

> ★ 2026-10 定案：**不另开常驻文字，直接用顶部情报按钮（index 5，三国杀模式用岚影刺图标；常规混战模式同一个按钮换成原版盟军间谍图标）的悬浮框**。

#### ★ 赤壁是什么形式？（本次查证的答案）

《赤壁 2.6》**没有"公屏播报某人身份"这种一次性事件**，它走的是**状态栏翻转**：

| 赤壁的做法 | 出处 |
|---|---|
| 每个玩家在记分板上有一行状态，按"观看者视角"渲染：<br>`身份：反贼 / 已阵亡` · `你的身份：主公` · `盟友` · `单向盟友` · `存活` | `Bang_159_code.txt:387-414` `BangGetDisplayStatus` |
| 记分板行标题 = `昵称/阵营色 + 主公标记 或 已阵亡标记`；主公标记**开局就公开** | `Bang_159_code.txt:416-427` `lorddeathdisplay` / `getPlayerDisplayName` |
| 玩家死亡时：`alive=false` → 隐藏他本人的身份面板 → **刷新所有记分板** → 再判胜负 | `Bang_162_code.txt:71-88` `onPlayerDeath` |
| 自己查身份：只私发给本人 | `Bang_160_code.txt:230` |
| 死亡时还要**删掉旧按钮重建**身份按钮，因为 `Desc` 无法实时更新 | `Bang_160_code.txt:710, 761` |

也就是说：**赤壁把身份揭示"做成了常驻信息"，而不是"播一条公告"** ——
死了以后那一行永久显示"身份 + 已阵亡"，谁想看随时能看到。
唯一的开局公开身份是**主公**（永远带标记）。

本图没有记分板身份位（本图记分板在 `20_hud.lua` 里被用来刷每人场上单位数），
所以这里取"公屏通报"这种等价形式：**效果一样（全图都知道他什么身份），实现更省**。
如果以后想完全对齐赤壁，落点是把 `20_hud.lua` 的记分板行文字改成
`单位数 + 身份/已阵亡`，不需要新增节点。

> 冀州 2.4 用的是取巧办法：小地图四角各留一小块只有特定玩家有视野的区域配文字，
> 拿「视野权限」当私有通道。2.6 已放弃，本文也不采用。

## 7 结盟系统（严格身份阵营）

### ① 底层原语 —— 源码级证据

《赤壁 2.6》的 `AllegianceModule` 全文就在 `Bang_30_code.txt` 里，**它就是一层薄封装**：

```lua
-- Bang_30_code.txt:20-34
set_allegiance_single_way(a, b, x)  →  ExecuteAction("PLAYER_RELATES_PLAYER", a, b, x)        -- 1 次
-- Bang_30_code.txt:41-56
set_allegiance_both_way(a, b, x)    →  上面那句正反各调一次                              -- 2 次
-- Bang_30_code.txt:62-74
get_player_relation(a, b)           →  exPlayerGetRelationShip(a, b)  →  0=Enemy / 1=Neutral / 2=Friend
```

结论：**引擎是方向性的，单向关系原生支持，不需要移植 LuaLib，也不需要实测。**

### ② 初始关系表（严格阵营）

| ↓ 我 \ 他是 → | 主 | 忠 | 反1 | 反2 | 内 |
|---|---|---|---|---|---|
| **主** | — | Friend | Enemy | Enemy | Enemy |
| **忠** | Friend | — | Enemy | Enemy | Enemy |
| **反1** | Enemy | Enemy | — | **Enemy → 可认亲** | Enemy |
| **反2** | Enemy | Enemy | **Enemy → 可认亲** | — | Enemy |
| **内** | **Friend（单向）** | Enemy | Enemy | Enemy | — |

### ③ 反贼之间的「认亲」

严格阵营下，**反贼互相不知道对方是反贼**，所以初始必须是 Enemy。
「结盟」在严格阵营下的唯一意义就是：**反贼之间双向认亲**（主忠之间天然友军，不需要动作）。

```lua
-- 认亲（双向）
ExecuteAction("PLAYER_RELATES_PLAYER", a, b, "Friend")
ExecuteAction("PLAYER_RELATES_PLAYER", b, a, "Friend")
```

认亲后，`BangGetDisplayStatus` 那条规则会让双方看到「双向盟友」，这就是反贼之间的
暗号 —— 和原作「反贼跳反」的体验一致。

### ④ 内奸 → 主公 单向 Friend

内奸的规则是「先保护主公，杀死所有其他玩家，最后再杀主公」。所以：

```lua
ExecuteAction("PLAYER_RELATES_PLAYER", 内奸, 主公, "Friend")   -- 内奸打不了主公
ExecuteAction("PLAYER_RELATES_PLAYER", 主公, 内奸, "Enemy")    -- 主公能打内奸
```

**这是全案唯一的单向关系**，也是「必须严格阵营」下依然要保留单向机制的原因。

### ⑤ 主公 ↔ `PlyrCreeps` 双向友军

照 `Bang_160_code.txt:797-801`：

```lua
ExecuteAction("PLAYER_RELATES_PLAYER", 主公, "PlyrCreeps", "Friend")
ExecuteAction("PLAYER_RELATES_PLAYER", "PlyrCreeps", 主公, "Friend")
```

理由：本图主公**没有位置优势**（岛是固定的，不像赤壁让主公坐中间），却要被 2 个反贼
+ 1~2 个内奸同时盯上。而 `17_ai.lua` 现在会把 `PlyrCivilian`/`PlyrCreeps` 的单位塞进
ATTACK 队主动打玩家 —— 给主公这条友军，中立怪就只打别人，正好补上他失去的地利。

## 9 胜负判定

### ① 赤壁原文（`Bang_162_code.txt:2-49`）

```lua
-- 第一段：主公「失去控制」（PW<主公> 不再归主公所有，且未被摧毁）
if lord_index ~= nil then
    if not EvaluateCondition("NAMED_OWNED_BY_PLAYER", ..., "PW"..lord)
       and not EvaluateCondition("NAMED_DESTROYED", "PW"..lord) then
        if rebel_alive == 1 and loyalist_alive == 0 and traitor_alive_count == 0 then return "反贼胜利"
        elseif loyalist_alive == 0 and rebel_alive == 0 and traitor_alive_count == 1 then return "内奸胜利"
        elseif loyalist_alive == 1 and rebel_alive == 0 and traitor_alive_count == 0 then return "主公和忠臣胜利"
        end
    end
end

-- 第二段：主公死亡
if lord_alive == 0 then
    if rebel_alive == 1 then return "反贼胜利"
    elseif alive_count == 1 and traitor_alive_count == 1 then return "内奸胜利"
    end
    return "无胜者"
elseif rebel_alive == 0 and traitor_alive_count == 0 then
    return "主公和忠臣胜利"
end
return nil                                      -- 游戏继续
```

### ② 移植版：删掉第一段 + 修正内奸判定

**删掉第一段**：它依赖 `PW<主公序号>` 这个具名对象（赤壁里是主公的主基地），
本图没有对应物，而 `craneN` 只会被摧毁、不能被占领 → 整段是死代码。

**修正内奸判定**（关键）：

- 原文 `alive_count == 1 and traitor_alive_count == 1` 在 **6 人局（2 个内奸）** 会提前判和：
  主公死 + 反贼已全灭 + 两个内奸都活着 → `alive_count = 2`、`traitor = 2` → 落到「无胜者」。
  可是两个内奸本该互相残杀到只剩一个。
- 原文还会在「主公死 + 无反贼 + 内奸活着 + 忠臣也活着」时立刻判「无胜者」，
  而按规则内奸还得先杀掉忠臣 → 这也是提前结束。

移植版：

```lua
function ChoukaBangCheckGameEnd()
    -- 统计（只在 ChoukaBangSeats 里数）
    local alive_count, lord_alive, loyalist_alive, rebel_alive, traitor_count = 0, 0, 0, 0, 0
    for k = 1, getn(ChoukaBangSeats), 1 do
        local i = ChoukaBangSeats[k]
        if ObjectIsAlive(GetObjectByScriptName("crane" .. i)) then
            alive_count = alive_count + 1
            local r = ChoukaBangRole[i]
            if r == "主公" then lord_alive = 1
            elseif r == "忠臣" then loyalist_alive = 1
            elseif r == "反贼" then rebel_alive = 1
            elseif r == "内奸" then traitor_count = traitor_count + 1
            end
        end
    end

    if lord_alive == 0 then
        if rebel_alive == 1 then
            return "反贼胜利"
        end
        if traitor_count >= 1 then
            if alive_count == traitor_count then
                return "内奸胜利"          -- ★ 场上只剩内奸（1 个或 2 个都算）
            end
            return nil                     -- 还有忠臣在打，继续
        end
        return "无胜者"                     -- 反贼、内奸都没了，主公也死了
    elseif rebel_alive == 0 and traitor_count == 0 then
        return "主公和忠臣胜利"
    end
    return nil
end
```

### ③ 与赤壁的差异对照

| 场景 | 赤壁 2.6 | 本方案 | 说明 |
|---|---|---|---|
| 主公失去控制（基地被占） | 三种即时判胜 | 无此分支 | 本图起重机不可占领 |
| 主公死 + 有反贼活 | 反贼胜 | 反贼胜 | 一致 |
| 主公死 + 无反贼 + 只剩 1 内奸 | 内奸胜 | 内奸胜 | 一致 |
| 主公死 + 无反贼 + **2 内奸**活着 | **无胜者（提前判和）** | 继续打 | 修正（6 人局必需） |
| 主公死 + 无反贼 + 内奸 + 忠臣都活 | **无胜者（提前判和）** | 继续打 | 修正 |
| 反贼+内奸全灭、主公活 | 主忠胜 | 主忠胜 | 一致 |

> 5 人局（1 个内奸）下，移植版与赤壁**行为完全一致**；修正只在 6 人局和上述边界生效。

### ④ 结算

判定出结果后：

### ★ `16_buttons.lua` 为什么要改，而不是"包装"

赤壁的做法是 `previous_custom_button_click = onCustomBtnClickEvent` 然后替换掉
（`Bang_159_code.txt:930-937`），但它那边 `onCustomBtnClickEvent` **只定义一次**。
本工程不一样：`16_buttons.lua` 是**1 秒常驻节点**，每秒都会重新定义这个全局函数
（`16_buttons.lua:511-513`）。所以「一次性包装」会在下一秒被踩掉。

而且这里还有一条更省事的路径：本工程的 `onCustomBtnClickEvent` **本来就是把参数原样转发**给
`onCenterTopBtnClickEvent`，两族按钮（顶部 `exCenterTopBtn*` 的自定义按钮 `exCreateCustomButton*`）
共用同一个入口。所以只需在**入口顶部**问一句：

```lua
function onCenterTopBtnClickEvent(playerName, btnIndex)
    if type(ChoukaBangOnBtn) == "function" then
        if ChoukaBangOnBtn(playerName, btnIndex) == 1 then
            return 1                       -- 三国杀认领：偏好卡 1201~1206 / 顶部情报按钮 5
        end
    end
    if btnIndex == CHOUKA_BTN_MARKET then  -- 其余照旧
        ChoukaShowMarketDialog(playerName)
    end
end
```

`ChoukaBangOnBtn`（在 `70_bang/32_bang_pref.lua`）第一句就判 `CHOUKA_MODE ~= 1 → return 0`，
外加 `type()` 存在性检查 —— 即使偏好节点整段没加载，也只是这个 `if` 被跳过，行为与改造前一致。

### ★ 实测只需确认 1 件事

前 3 项都有生产级先例，真正的未知只剩一个：**自定义按钮的坐标原点与 index 上限**。
所以最小验证脚本只做一件事 —— 「给 Player_1 在屏幕中央画 3 个 200×200 按钮，
点第几个就往公共板打一行 `clicked N`」，跑通即可撤掉。

### 自定义按钮的完整参数（DSA `02_event.lua:402-410` + `教程.lua:607`）

```lua
exCreateCustomButtonForPlayer(playerName, {
    Index      = 1201,          -- 全局唯一，自己分段
    TextureName = "Button_AlliedAntiInfantryInfantry_on",  -- 或数字图片 ID
    Desc       = "悬停提示文字",
    X = 123, Y = 284,           -- 逻辑分辨率 1366×768 下的像素坐标
    SizeX = 200, SizeY = 200,   -- 显式尺寸，不依赖贴图原尺寸
    GroupIndex = 1200,          -- 同组可整组操作
    AlignX = "left", AlignY = "top",
})
exCustomBtnSetVisibilityForPlayer(playerName, 1201, 1)
exCustomBtnSetSelectedForPlayer(playerName, 1201, 1)
exCustomBtnSetEnableForPlayer(playerName, 1201, 1)
exCustomBtnRemoveForPlayer(playerName, 1201)
```

> 热键实现细节（P2 用）：
> `exRegisterHotKey(188, 0, cmd)` = 逗号（`VK_OEM_COMMA = 0xBC`，不在 `KeyboardKeyCodeEnum` 里，
> 赤壁注释原话「KeyboardKeyCodeEnum does not define comma」）；
> `exRegisterHotKey(49..57, 18, cmd)` = Alt+1..9（`ALT = '12'` = 18，`K_1..K_9 = '31'..'39'` = 49..57）；
> 监听函数是固定名 `onUserHotKeyEvent(playerName, commandCode, mouseWorldPos)`。
> **不需要 LuaLib**，直接调原始 `exRegisterHotKey` 即可。
> `exRegisterHotKey` **只注册一次**（用守卫标志），`onUserHotKeyEvent` 每秒重定义。
